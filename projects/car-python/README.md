# 辰龙 Python 小车编程

当前仓库包含三个逐级增加目标物、混淆物、障碍物与有序途径点数量的“广阳岛综合任务”。任务1 要求把红色目标包裹送到绿色存放点、把蓝色混淆包裹完整移出任意道路边界、绕开障碍物，依次完成 4 个巡检点后返回停车区。当前比赛规则只对驶出道路和碰撞扣分，不设置超速、逆行、红灯或禁行区规则。系统同时包含数据驱动道路、纯核心 `TaskEngine`、100 分实时评分、20ms 固定步长车辆仿真、v4 客户端运行记录，以及隔离执行重放的本地 Node 校验后端。它不是官方权威判分系统；实现范围与后续开发边界见 [`docs/广阳岛仿真系统开发说明.md`](docs/广阳岛仿真系统开发说明.md)。

广阳岛场景直接使用 `word/广阳岛仿真沙盘地图.png` 的主体区域作为地图纹理，按图中约 5m × 3m 的比例映射；规则道路由同一原图的像素坐标标定。

广阳岛采用“原图底图 + 像素地形 + 立体浮雕”分层渲染：斜视和跟随视角会从原图边缘识别外部水域，生成平滑的岛岸高差，并显示双层树冠、建筑、湖面、花田、梯田与标志；规则道路走廊保持平整。俯视视角隐藏地形与浮雕，继续显示可直接核对的原始平面底图。原图中的静态蓝色示意车会在运行时修补掉，由可运行的小车替代。

3D 模拟模式的视觉接口使用车体上的 640×480 虚拟摄像头：场景先渲染为 RGB 像素，再由固定版本的本地视觉管线识别红色目标物、黄黑障碍物、蓝色混淆物和绿色存放点；`robot.sees()`、`robot.detect()`、`robot.observe()`、`robot.direction()` 与 `robot.approach()` 不直接读取场景物体坐标。“摄像头识别练习”不是训练模型，而是在同一张地图上练习程序读取 `observe` 结果、作出动作并查看反馈；它会关闭正式比赛场次与成绩提交。“示例”菜单只载入不含坐标、对象编号或完整比赛路线的视觉 API 示例。

页面可切换到“真实小车（不计分）”。该模式会显示小车摄像头实时画面，并向局域网小车发送前进、后退、左右转、等待、抓取、松开和停止等基础指令；摄像头画面只供人工查看，不会提供给 Python、保存或上传，实车也不提供定位、传感或任务状态回传，程序使用这些接口会在移动前被拒绝。实车运行不会创建比赛场次、保存记录或生成分数。由于浏览器的混合内容和本地网络访问限制，HTTP 小车应使用同一局域网内的本地 HTTP 页面控制，不能依赖公网 HTTPS 页面。

`robot.observe("目标物")` 会返回同一摄像头帧中的安全感知摘要（固定英文类别码、中文类别、方位、估算距离、置信度和稳定状态），不会返回世界坐标或内部物体编号；`robot.holding()` 返回夹爪当前持有的“目标物”“混淆物”或 `None`。比赛虚拟视觉始终启用同一组内置类别，并禁用用户模板和通用 YOLO 回退，避免根据场景真值开关检测器。摄像头输出用于学生程序决策，任务得分仍由确定性的物体位置、任务区域和碰撞状态计算。

`robot.approach()` 会根据摄像头画面实际执行小步转向和前进，并服从各类别的安全操作距离；自动前进脉冲不超过 30% 速度。广阳岛使用每米 8 个高精度仿真单位，冻结车辆上限折算为 31.25 cm/s，自动靠近不超过 9.375 cm/s。抓取物靠近到夹爪可达范围，存放点则在约 13.5 cm 处停止，便于随后调用 `robot.release()`。混淆物没有固定“清理点”；释放后会用冻结的道路几何、物体半径和最小安全净距判断其整个圆盘是否已经移出任意道路边界，不会把世界坐标交给学生程序。

广阳岛提供六个只读导航传感接口：`robot.mission()` 返回当前服务端冻结地图中停车点、存放点、四个途径点和返航点的**道路级锚点**（只含 `roadId` 与 `progressCm`，不含坐标）；普通单局还返回三类任务物体的道路级锚点（`role/roadId/progressCm`），让程序可以真正按拓扑规划，抵达后仍须用摄像头确认并完成抓放；练习/筛选五局的私有布局不返回这些物体锚点。`robot.task_state()` 返回任务引擎实际确认的进度、下一途径点、两类物体处理状态、避障状态与返航状态；`robot.release_preview()` 在夹爪持有物体时，确认按当前姿态释放是否可执行、是否会完成对应投放、以及混淆物离全部道路边缘的最小余量（不返回预落点坐标或对象编号）；`robot.odometry()` 返回相对本次程序起点的前向/右向位移、相对航向与累计里程；`robot.road_state()` 返回当前道路、道路进度、两端节点、节点/出口、中心偏移、左右余量和前方净空；`robot.map_graph()` 返回不含坐标的公开道路节点与边。它们不返回世界坐标、推荐出口或最短路线，也不会替学生程序自动寻路或绕障。正式运行中的导航查询会写入 v4 输入账本，并由确定性回放根据冻结道路、车辆、任务和动态碰撞状态重新计算；每场最多记录 1,000 次导航查询。

在此基础上，广阳岛提供两个**局部道路控制**，但没有官方自动寻路 API：

当前新场次冻结 `chenlong.navigation/v6` 与 `chenlong.navigation-control/v8`。5m × 3m 地图虽然内部保留每米 8 个高精度仿真单位，但 `robot.forward(厘米)`、`robot.backward(厘米)`、`progressCm`、`distanceCm`、`max_cm`、路口半径和驶入出口距离都按真实物理厘米换算；例如 `robot.forward(50)` 在无阻挡时恰好前进 50 厘米，即 4 个内部仿真单位。`take_exit()` 默认会实际进入约 25cm。旧 v5/v7 记录继续使用原换算逻辑，保证历史回放不被新版控制器改写。

- `await robot.forward(distance_cm)` / `await robot.backward(distance_cm)`：按厘米前进或后退，只填写一个参数，范围为 0.1～500 厘米。仿真器以固定 20ms 步长换算并执行，不再接收时间和速度参数。
- `await robot.follow_road(max_cm=100, speed=40, obey_speed_limit=False)`：只沿**当前道路**短程居中行驶。`max_cm` 必须在 10～500 厘米之间，`speed` 必须在 10～100 之间；设为 `obey_speed_limit=True` 时，会在每个仿真 tick 按冻结道路与限速区自动钳制实际速度，但当前任务不设置超速扣分。它不会代替学生寻找节点、选择出口或绕开障碍。达到距离上限或遇到道路节点、道路端点、前方障碍/边界时停车。若返回 `junction` 后立即读取的 `road_state()["atNode"]` 仍为 `False`，只执行一次 `robot.forward(2)` 并重读传感器，确认进入节点后再选出口；不要盲目循环前进。
- `await robot.take_exit(road_id, speed=30, obey_speed_limit=False)`：只在当前道路节点驶入学生从 `robot.road_state()["exits"]` 中自行选定的相邻 `roadId`。速度可设 10～100；设为 `obey_speed_limit=True` 时，进入道路的全过程也会逐 tick 按冻结道路和限速区钳制实际速度。叶端非单行道路可选择当前 `roadId` 原路折返；不存在/禁止驶入的出口或逆单行方向时不会替学生改选其他道路。

两个方法都返回恰好五个字段：`accepted` 表示请求是否具备执行条件，`stoppedBy` 表示停止原因，`roadId` 表示当前或选定道路，`distanceCm` 表示本次实际行驶距离，`elapsedTicks` 表示本次消耗的 20ms 仿真 tick 数。常规停止原因为 `max_distance`、`junction`、`road_end`、`front_clearance` 和 `entered_road`；条件不满足时为 `off_road`、`wrong_way`、`not_at_junction` 或 `invalid_exit`；`collision`、`safety_limit`、`time_limit` 表示碰撞兜底、单动作安全上限或比赛时限终止。对于两端路口判定范围重叠的短道路，当前控制器会驶到实际选定端点后再报告 `junction`，保证随后的 `road_state()["nodeId"]` 与可选出口一致；不需要用固定角度或距离去绕过这一类边界。

局部道路控制每场最多 300 次，与 1,000 次只读导航查询预算相互独立。参数格式有效的请求即使返回 `accepted: false` 也占用一次控制预算。每次调用会作为一个完整动作执行，并以一条 `navigation_control` 写入 v4 输入账本；如需在行驶中频繁重新观察，应减小 `max_cm` 并分多次调用。服务端回放同一冻结控制器并严格核对结果与最终车辆状态；它提供的是“当前道路短程循路 + 执行指定出口”，路线搜索、出口决策和避障策略仍必须由参赛程序完成。

模拟车辆的前进、后退、定时转向、角度转向、等待和规定时长的机械臂动作均按固定 tick 执行。运行结束后可直接点击“回放本次运行”；页面刷新后再次点击时，会从当前登录账户的后台存档自动载入最近一次记录。v4 记录从基础控制、局部道路控制、抓放和人工介入输入重新计算车辆、包裹、任务、规则与分数，并重新投影导航查询结果；原始遥测、事件和客户端结果只作为一致性校验，视觉查询同时保存带 SHA-256 的 PNG 证据。v3 保留车辆级确定性回放，v2 仅作非确定性的遥测播放。所有本地回放仍是调试能力，不是权威成绩复核。

## 启动

项目包含浏览器前端、Web Worker、WebAssembly 和本地校验后端，不能直接双击 `index.html`。

1. 安装 Node.js 18 或更高版本。
2. 在本目录打开终端。
3. 运行：

```bash
npm start
```

4. 浏览器访问：

```text
http://127.0.0.1:6178/
```

停止服务：回到终端按 `Ctrl+C`。

`npm start` 会由同一个 Node 进程托管网页，并提供注册、登录、个人记录、管理员记录、管理员用户管理、管理员地图发布、健康检查、临时校验、单局场次、五局评测和提交归档 API。注册时必须选择小学组、初中组或高中组；升级前的 `primary_low`、`primary_high`、`primary_school`、小学低年级组和小学高年级组等旧值都会安全合并为 `primary`（小学组），`middle_school` 和 `high_school` 分别迁为初中组和高中组，队伍、用户及历史成绩标识保持不变。当前认证数据结构为 `chenlong.auth-store/v6`，旧 v1–v5 数据会在下次停服重启时校验并原子迁移。首次注册的账号自动成为本地管理员，后续账号为普通用户；密码使用带随机盐的 scrypt 哈希，登录凭据使用 `HttpOnly; SameSite=Strict` Cookie，浏览器脚本和磁盘都不会保存明文凭据。仿真首页、个人记录页和管理后台均由服务端执行登录或角色门禁。

认证服务默认支持 2,000 个账号和 8,000 个活动登录会话。密码校验默认同时执行 2 个，额外请求进入最多 2,000 个位置、最长等待 120 秒的 FIFO 队列，不再因短时并发超过 2 个而立即失败。报名默认开放，并采用全局 5 分钟 2,400 次尝试的有界限流；报名结束后可通过 `CHENLONG_REGISTRATION_OPEN=false` 关闭新账号，已有账号登录不受影响。账号、会话、密码并发与队列、报名窗口均可通过环境变量调整，变量名、默认值和首次管理员的例外规则见 [`DELIVERY.md`](DELIVERY.md#账户容量与报名控制)。

官网免密入口为统一网关的 `/sso/jump`。生产环境必须设置独立的 `CHENLONG_OFFICIAL_SSO_SECRET`（至少 16 个 UTF-8 字节，建议使用高强度随机值）并仅通过 HTTPS 暴露。该密钥不同于子项目间使用的 `CHENLONG_PLATFORM_SSO_SECRET`，不得写入源码、日志或前端。官网传来的用户与队伍编号只在管理员用户接口中提供给成绩关联，普通用户资料不会返回这些编号。

所有认证写操作还共享同一条 FIFO 持久化队列：默认最多聚合 32 项或等待 10 毫秒，只在整批账号快照完成原子落盘后返回成功和登录 Cookie。批内单项校验失败不会影响其他项，整批写盘失败也不会提前改变内存状态或发出无法在重启后恢复的会话。

登录后，任务每次运行前会取得服务端 `sessionId/runId/challengeDigest`，并把场次永久绑定到当前账号；`challengeDigest` 是加入服务端随机数的场次承诺，浏览器拿不到服务端随机数或真实定义摘要。三个任务分别维护 8、10、12 套公开比赛地图，服务端使用不可由浏览器指定的队伍内部编号，为每支队伍在每个任务中稳定分配一套；同队多个账号取得相同地图，修改队伍显示名称不会重新抽取。普通单局会取得本队当前地图及为该场冻结的运行定义。单局结束后会自动保存到“我的比赛记录”，不会阻止下一次运行；弹窗顶部显示三个任务各自已正式提交的最高分，需要正式提交时在对应记录行点击“提交”。普通用户只能查看自己的普通单局记录。管理员后台只列正式提交的普通单局，可按用户名、队伍名、任务和校验状态筛选，可按最新提交或分数排序，也可切换“每队每任务最高分”；记录与用户列表分别分页。正式记录下方按 15 队一页汇总各队三项最高分，同时显示所在小组与三项总分，并可单独导出 CSV。管理员详情按需读取并显示该次提交的完整 Python 源码，列表与 CSV 不批量携带源码；后台可分别导出用户和当前筛选后的正式记录 CSV。服务端还会从通过回放核验的类型化输入账本中判断记录是否实际使用导航传感或局部道路控制，并只在管理员记录列表和详情中显示能力标记；源码注释和字符串不会产生该标记。记录、校验报告、账号哈希、会话哈希和已发布地图均原子写入 `.runtime/`，该目录已被 `.gitignore` 排除。

本地场次使用一次返回的 Bearer token；服务端磁盘只保存 token 的 SHA-256。提交必须同时匹配场次、运行号、队伍、地图/规则版本及服务端赛题定义摘要，服务端再使用自己保存的定义重放，而不是信任记录内的定义。完全相同的原始 JSON 字节可安全重试并返回同一个提交号。所有回执仍明确为 `authoritative: false`。

## 管理员地图发布（普通单局）

管理后台中的“广阳岛地图设置”默认折叠。三个任务可分别选择并编辑地图 1～8、1～10、1～12；“查看队伍地图分配”会列出队伍成员，以及该队伍在三个任务中分别取得的地图编号。展开编辑器后可在底图上拖动，或用坐标输入框精确调整共 8 个点位：4 个有顺序的途径点、目标物、目标点（绿色存放点）、混淆物和障碍物。保存不是单纯修改画面：服务端会再次检查字段和坐标格式、地图边界、道路可达性、与停车区的道路连通性、各对象/途径点/停车起终点的安全间距，以及障碍物是否仍给车辆留下可绕行空间；任一条件不满足都不会发布。

每次内容实际发生变化的成功发布都会生成递增的 `revision`、地图摘要和对应 `mapVersion`。保存请求携带编辑开始时的 `baseRevision`；若另一位管理员已经先发布，服务器会拒绝旧版本覆盖，管理员应保留草稿、重新加载最新版本并确认后再保存。不要直接编辑磁盘上的发布文件。

登录或重新选择任务时，学员页面会取得当前队伍在该任务中获配的布局；真正开始一次新的普通单局时，服务端会把当时的 `revision`、摘要、`mapVersion` 和完整运行定义一起冻结到该场次。之后管理员再次发布不会改变已经创建或正在运行的场次，也不会改写历史记录；该队伍下一次新建场次才会使用所分配地图的新版内容。地图编号由任务和队伍内部编号稳定确定，编辑地图不会让队伍换图。管理员自定义地图当前只用于**新建的普通单局**；练习五局（`batch`）和筛选五局（`ranked`）仍使用原有冻结的服务端私有布局与版本注册表。

每个任务的地图 1 沿用原发布目录，其他地图保存在对应任务目录的 `map-02`、`map-03` 等子目录中。不要依赖单个文件路径做备份；所有地图必须和账号、队伍、会话及比赛记录一起随整个数据目录完整备份、恢复和迁移。

## 兼容的五局后端（当前学员页面不启用）

按当前产品要求，学员工作台不显示练习五局和筛选五局入口，正式记录只采用逐条提交。仓库仍保留以下版本化后端和自动化夹具，用于旧数据回放与内部稳定性研究，不属于当前页面功能：

- **练习五局（本地参考，不入榜）**：每个账号最多同时保留 2 个未结束练习，最多创建 20 次。练习继续使用兼容的 v1 六套目录，适合调试一份代码在不同布置下是否稳定。
- **筛选五局（本地参考）**：每个账号在固定赛季 `2026-r2-gyi-local-screening.1` 只有一次机会。二次确认后立即冻结 Python 源码和队伍；关闭、过期、异常或缺局都会保留在这唯一一次结果里，不能换卷或再取最好成绩。所有账号使用同一份经过验收的 v2 五局 holdout form，服务端只随机改变五局顺序。

两类流程都会自动、串行完成 5 局；批次开始后不能在局间修改源码。5 局都使用广阳岛正式地图和同一任务规则，只改变三类物体的服务端私有布置，不创建额外地图。系统一次只下发当前局；当前局运行记录经服务端确定性重算并原子写入后，才会推进到下一局，不能跳局，也不会提前把未来局布局放入页面缓存。

设服务端确认的 5 个单局分数为 `s1`～`s5`，每局满分 100。`invalid`、`timeout` 和 `missing` 都按 0 分计入固定的 5 局分母；其中主动停止、批次过期或未完成而关闭造成的剩余局为 `missing`。最终分数为：

```text
五局均分 = (s1 + s2 + s3 + s4 + s5) / 5
五局总分 = 70% × 五局均分 + 30% × 五局最低分    （满分 100）
```

私有目录现在采用版本注册表：原有 6 套 `2026.08-private-layouts.1` 完整保留为兼容目录，旧批次仍按原 HMAC 顺序和承诺精确重算；新增冻结的 `2026.08-private-layouts.2`。v2 对 6 个目标物锚点、6 个混淆物锚点和 6 个障碍物锚点的 216 个组合逐一执行原有严格校验，排除 18 个物体净间距不足 15.625 cm 的组合，显式保留 198 套，不在运行时随机拼装未经验证的布局。

内部可解性工具已对 v2 的 198 套逐套使用正式 task/v5、交互、规则、车辆仿真和公开动作范围完成 `8/8`，198 套均零碰撞、零违规；参考时间为 95.98–223.04 秒，参考分数为 95.7–100.0 / 100，全部远低于 600 秒时限。固定 ranked 表单包含 5 套，分别接近全目录参考时长的 P10、P30、P50、P70、P90，且三类锚点在 5 套内各自不重复；其余 193 套已冻结为与 ranked 完全不交叉的候选练习池。当前 20 次“练习五局”入口仍使用兼容的 v1 六套目录，193 套池将在练习迁移完成并重新验收后才启用。两种 v2 选择使用带 purpose 的独立 HMAC 域。命令行报告只公开数量、分位数和验收结果，不把布局编号、参考路线、锚点或坐标放入网页资源。

页面刷新后不会自动重跑学生程序。练习使用 `sessionStorage` 作为同一标签页的恢复快路径，并可通过账号级未结束练习摘要让用户显式选择恢复或关闭；摘要不返回源码、当前/未来布局、场次或运行定义。筛选的所有者接口会把唯一一次筛选的锁定源码、队伍和服务器截止时间返回给本人，以免浏览器存储丢失导致唯一机会无法恢复；这些字段不会进入匿名榜单。恢复当前局时仍继续使用该局原有的 `sessionId/runId/runDefinition`，只有服务端已经确认的局才算推进。

“同时 2 个、累计 20 次”只适用于练习，不是筛选重考次数。筛选按 `(赛季, 登录账号)` 永久保留唯一一次创建记录；创建中断时只有完全相同的源码和队伍可以恢复，其他输入会被拒绝。单局场次的有效期会钳制到父批次截止时间，完成、关闭或过期后立即释放对应运行名额，同时保留可审计归档。服务端还会对同一数据目录取得单主机、单 Node 写进程锁；第二个活动写进程会启动失败，避免本地文件状态被多个服务进程同时修改。进程异常退出留下的锁也会安全拒绝启动，必须在确认旧进程已停止后由运维显式清理；系统不会冒险自动回收。这不是多主机分布式锁。

筛选榜按五局总分、完成局、有效局、最低分、均分、异常/缺失/超时局和安全事件依次比较；十项完全相同才并列，私有稳定键只固定显示顺序，不改变名次。这套机制仍是可审计的本地多局评测，不是强反作弊：当前局必须在本地浏览器渲染和执行，熟悉开发者工具的人仍可检查当前布局；固定同卷只适合封闭或近同步的本地筛选。系统保证的是未来布局不提前下发，并通过同源多布置降低硬编码脚本的稳定性。所有批次和榜单响应仍为 `authoritative: false`。五局模式也不会增加自动寻路能力；程序仍只能使用导航传感器、基础运动和 `follow_road` / `take_exit` 这两个有界局部控制，自行完成路线搜索、出口选择、避障和物体处理。

仅调试静态资源服务器时仍可执行：

```bash
npm run start:static
```

当前版本要求登录后才可使用仿真，因此纯静态服务器不提供可用的登录、比赛或记录功能；正常使用必须运行 `npm start`。

## 运行要求

- 推荐使用最新版 Chrome 或 Edge。
- 必须保留 `python-worker.js` 和整个 `vendor/` 目录的相对位置。
- Python、视觉运行库和 YOLO 模型均位于本地 `vendor/`，启动仿真不依赖第三方 CDN；通过 HTTP 提供整个目录即可。
- 视觉接口使用模拟器内置的虚拟摄像头，不需要浏览器摄像头权限或外部设备。

校验一份导出的运行记录：

```bash
npm run verify:record -- path/to/RunRecord.json
```

校验器只输出 JSON 报告：`verified` 表示基础控制、导航查询、局部道路控制、物理、交互、任务、规则和成绩这些确定性范围已完整重算，记录内部一致且原始结果字段完整匹配；`partial` 表示旧版遥测、确定性重算未完成或缺失完整对照结果；`invalid` 表示记录损坏或与重算结果冲突。报告中的 `navigationQueriesRecomputed` 与 `navigationControlsRecomputed` 分别说明导航投影和有界控制是否完成重算。视觉查询不会因为诚实保留在记录里而把状态降为 `partial`：当前检测器没有在重放端执行时，报告会保持 `capabilities.recomputationComplete: false`，同时给出 `capabilities.deterministicRecomputationComplete: true`、`visionStatus: "not_recomputed"` 和 `vision_detections_not_recomputed` 限制码。报告始终包含 `authoritative: false`；正式成绩仍需服务端签名任务与输入后重放。

浏览器中的“服务端校验”按钮调用同一校验核心。后端把 JSON 解析和重放放在独立 Worker 中，并限制请求体、运行时间和并发数；默认同时使用 4 个校验 Worker，额外请求进入最多 512 个位置、最长等待 90 秒的 FIFO 队列，浏览器与服务端请求等待上限为 120 秒。可用 `CHENLONG_MAX_CONCURRENT_VERIFICATIONS`、`CHENLONG_MAX_QUEUED_VERIFICATIONS`、`CHENLONG_VERIFICATION_QUEUE_TIMEOUT_MS` 调整。普通单局默认保留 600 个活跃场次，练习与筛选各保留 200 个，总活动上限仍为 1000；已经提交或过期的历史目录不再占用活动场次配额，也不存在累计一万目录后永久拒绝新运行的问题。原始历史仍由磁盘字节预算保护，默认 512 MiB，可通过 `CHENLONG_RUN_ARCHIVE_MAX_BYTES` 配置，范围不得超过 10 GiB；应根据正式磁盘容量、单条记录实测大小和备份周期设置，存满时明确返回 507，系统不会自动删除比赛记录。

官网成绩内部接口不再读取“最近一万条”。服务首次需要成绩时从全部耐久的普通正式提交构建“用户 × 提交时队伍 × 任务”最高分聚合，随后每次成功归档都会增量维护；后续低分只推进该项最后更新时间，不会覆盖历史最高分。提交时的不可变队伍 ID 属于聚合键，即使官网 SSO 后续把该用户映射到另一队，旧队成绩也不会迁移，同时新队后续提交不会被旧队高分遮蔽。个人与管理员记录列表仍使用服务端分页，旧的不带分页参数请求返回最近 1000 条兼容结果。页面将 `verified` 展示为“确定性校验通过”，视觉未重算会作为限制单独显示。该状态不代表客户端提供的任务定义、输入或视觉判断可信。
