# Python 子项目交付与部署说明

本文件用于 Python 子项目的数据维护、升级和故障排查。正式比赛应从统一平台根目录启动，统一入口、依赖安装、官网接口和公网安全要求以 [`../../DELIVERY.md`](../../DELIVERY.md) 为准。统一交付最低要求 **Node.js 22.13**。

Python 的浏览器运行资源随项目本地提供；但不能据此假定整个统一源码包都无需安装依赖。Windows 即用包通常包含识物工坊依赖，源代码包、缺失依赖的包或其他操作系统/CPU 架构仍须按根目录交付说明执行可复现安装。

## 1. 首次本机初始化

正式数据应保存在安装包之外的受控绝对路径中。以下示例在 `projects/car-python/` 内执行，尖括号内容必须替换为本机实际受控目录，不依赖开发机盘符：

```powershell
$env:CHENLONG_DATA_DIR = '<受控数据目录>\car-python'
npm start
```

默认仅监听 `http://127.0.0.1:6178`。这只用于隔离维护或完全空库初始化：若确实部署空数据，可仅从本机回环地址注册第一个管理员，随后立即停止独立服务并改用统一平台启动。正式交付快照应使用赛务方另行保管的现有管理员凭据；活动会话已清除，凭据不能写入交付包。不要把尚未初始化的系统或 Python 子服务直接暴露到公网。

## 2. 统一平台 HTTPS 上线

正式反向代理应负责 HTTPS，并且**只**把请求转发到统一网关 `127.0.0.1:6190`，不得直接转发 Python 的 `6178`。在统一平台根目录设置：

```powershell
$env:CHENLONG_PLATFORM_PUBLIC_ORIGIN = 'https://contest.example.com'
$env:CHENLONG_PLATFORM_TRUSTED_PROXIES = '<直连可信代理的精确 IP>'
.\START-WINDOWS.cmd
```

`CHENLONG_PLATFORM_PUBLIC_ORIGIN` 必须与参赛者实际访问的 HTTPS 来源完全一致（协议、域名和非默认端口），不要填写路径、查询参数或结尾斜杠。统一启动器会把该值安全传递为 Python 子服务的来源和 Secure Cookie 配置。可信代理只列实际与服务器直连的精确 IP，并由代理清洗客户端自带的转发头；临时隧道域名不能作为正式配置。

### 账户容量与报名控制

默认认证容量为 2,000 个账号、8,000 个活动登录会话、每个账号最多 20 个会话。密码哈希默认同时执行 2 个，其余请求按到达顺序进入最多 2,000 个位置的队列，等待超过 120,000 毫秒会返回可重试错误。默认报名限流为整个服务进程每 5 分钟最多 2,400 次尝试，足以覆盖一次 2,000 人集中开放报名；限流按服务进程全局计算，避免反向代理把所有参赛者显示为同一个本机地址时误伤。

账号、登录会话、注销、过期会话清理和管理员用户修改共享同一个 FIFO 单写队列。服务默认收集最多 32 项或等待最多 10 毫秒（先满足者先提交），按顺序验证后只生成一次完整账号快照并执行一次原子写入。单项业务校验失败只拒绝该项，不会污染同批其他状态；整批磁盘写入失败时，所有尚未返回的成功项都会失败，内存状态保持原值。登录 Cookie 只有在包含该会话的快照完成同步和原子替换后才会返回，因此批量提交不会牺牲重启后的会话持久性。

可在启动前按实际压测结果设置以下变量；所有数值都必须是正整数，布尔值必须明确写成 `true` 或 `false`：

```powershell
$env:CHENLONG_MAX_USERS = '2000'
$env:CHENLONG_MAX_AUTH_SESSIONS = '8000'
$env:CHENLONG_MAX_AUTH_SESSIONS_PER_USER = '20'
$env:CHENLONG_MAX_PASSWORD_OPERATIONS = '2'
$env:CHENLONG_MAX_PASSWORD_QUEUE = '2000'
$env:CHENLONG_PASSWORD_QUEUE_TIMEOUT_MS = '120000'
$env:CHENLONG_MAX_REGISTRATION_ATTEMPTS = '2400'
$env:CHENLONG_REGISTRATION_WINDOW_MS = '300000'
$env:CHENLONG_REGISTRATION_OPEN = 'true'
```

报名结束后可将 `CHENLONG_REGISTRATION_OPEN` 改为 `false` 并重启，已有账号仍可登录。为了避免全新部署被永久锁在系统外，即使该值为 `false`，空账号库仍只允许首个成功注册的账号成为初始化管理员；该账号写入后，其余注册立即关闭。健康检查的 `capabilities` 会返回当前账号容量、密码队列和报名开关配置，便于上线前核对。不要把提高密码并发数当作提高吞吐量的唯一手段；应在正式机器上观察 CPU、内存和响应时间后再调整。

## 3. 数据与单写进程

### 官网 SSO

生产环境设置 `CHENLONG_OFFICIAL_SSO_SECRET` 后，官网可跳转到统一入口 `/sso/jump`。密钥至少 16 个 UTF-8 字节，建议由密码管理器生成并只注入服务端环境；不要使用接口文档示例值，也不要与 `CHENLONG_PLATFORM_SSO_SECRET` 共用。入口严格要求 `user_id`、`team_id`、`group_type`、`team_name`、`timestamp`、`sign` 六个唯一参数，时间窗口和防重放窗口均为 5 分钟。同一官网用户首次登录后固定绑定官网队伍编号；同队名称或组别更新会同步整队，不同队伍编号会返回 1004 并在审计中记录 `OFFICIAL_TEAM_REASSIGNMENT_REQUIRES_ADMIN`，正式转队只能走管理员离线审核流程。启用该入口时统一平台会强制要求 HTTPS `CHENLONG_PLATFORM_PUBLIC_ORIGIN`，否则拒绝启动；`CHENLONG_OFFICIAL_SSO_ALLOW_INSECURE_TEST_MODE=true` 只能用于隔离的自动化测试。审计与防重放数据保存在 `CHENLONG_DATA_DIR/official-sso/`，备份正式数据时必须一并保留。审计日志默认每个 4 MiB、最多保留 5 个文件，可用 `CHENLONG_OFFICIAL_SSO_MAX_AUDIT_BYTES` 和 `CHENLONG_OFFICIAL_SSO_MAX_AUDIT_FILES` 在有容量规划时调整；审计磁盘故障会计入健康状态，但不会把已成功创建的登录会话变成错误页。SSO 默认按 5 分钟全局 4,000 次、单 IP 1,000 次限流，可用 `CHENLONG_OFFICIAL_SSO_RATE_WINDOW_MS`、`CHENLONG_OFFICIAL_SSO_MAX_ATTEMPTS`、`CHENLONG_OFFICIAL_SSO_MAX_ATTEMPTS_PER_IP` 调整。公网反向代理必须启用 HTTPS，并在统一网关 `CHENLONG_PLATFORM_TRUSTED_PROXIES` 中只列出直连可信代理的精确 IP，由代理清洗并传递 `CF-Connecting-IP` 或 `X-Forwarded-For`；未列入的客户端头会被忽略。

官网 SSO、成绩 AppSecret、RSA 公钥配置、IP 白名单、晋级文件和冻结快照都不随普通交付 ZIP 提供，必须由赛务方通过受控环境另行注入。RSA 私钥只保留在官网侧。

- `CHENLONG_DATA_DIR` 必须是安装包外的绝对路径，且运行账号需要读写权限；不要使用包内默认数据目录承载正式数据。
- 同一数据目录在任何时候只能由一个 Node.js 进程使用。不要让本机启动实例、后台服务或不同版本同时指向同一目录。
- 若出现写入锁提示，先确认旧进程已经完全退出；不要在进程仍运行时删除锁文件。

## 4. 升级

升级前正常停止旧服务并完成备份。把新版本解压到一个新目录，继续通过 `CHENLONG_DATA_DIR` 指向原来的包外数据目录，再启动并检查健康状态。不要用新包覆盖旧程序目录，也不要删除或覆盖数据目录。

## 5. 备份与恢复

备份时先停止全部统一平台服务，再完整复制整个 `CHENLONG_DATA_DIR`，并妥善保护备份中的账号、比赛数据和管理员已发布地图。三个任务共含 8、10、12 套地图，发布文件分布在任务目录及其 `map-02`、`map-03` 等子目录；不要只备份某一个地图文件、账号或记录子目录。

普通交付 ZIP 不包含管理工作区的 `record-backups/`，交付快照也不能替代恢复备份。正式升级前须另外制作加密冷备份、记录校验摘要并完成恢复抽查。

恢复时先停止服务，将完整备份恢复到一个确定的包外绝对路径，确认权限正确，再设置 `CHENLONG_DATA_DIR` 并启动。恢复期间不得有其他进程同时访问该数据目录。

## 6. 健康检查

统一平台正式检查：

```powershell
Invoke-RestMethod http://127.0.0.1:6190/api/health
```

应返回 HTTP 200，且响应中的 `status` 为 `ok`。反向代理上线后，还应访问 `https://实际域名/api/health` 确认公网链路正常。只有隔离维护时才直接检查 <http://127.0.0.1:6178/api/health>，该端口不得对参赛网络开放。

## 7. 管理员用户管理

管理员登录管理后台后，可以在“用户管理”中查看账号列表，并按用户名、队伍名、参赛分组和角色筛选。列表每页显示 20 条，筛选条件作用于全部用户并从第一页重新展示；用户分页与正式提交记录分页相互独立。这里仅允许修正普通用户的队伍名和参赛分组；管理员账号不参与队伍或分组管理，也不提供删除账号、修改角色或重置密码的操作。修改保存后，其他管理列表和记录筛选会使用新的队伍名和参赛分组。

用户管理接口与页面都需要管理员身份。接口不会返回密码哈希、登录凭据或会话信息；不要通过复制数据目录或修改其中的账号文件来代替后台操作。

“正式提交记录”只显示学员主动提交且通过归档流程的普通单局记录。后台可按用户名、队伍名、任务和校验状态筛选，可按最新提交或分数排序，并可切换为“每队每任务最高分”。管理员打开单条详情时才读取该次提交的完整 Python 源码；列表和 CSV 导出不批量包含源码。用户列表和当前筛选后的记录可分别导出 CSV，导出前仍应确认页面筛选条件符合用途。

活动场次容量与历史目录数量已经分离，累计历史超过一万目录也不会永久阻止新运行。官网成绩使用全部耐久普通提交构建并增量维护“用户 × 提交时队伍 × 任务”最高分聚合，后续低分不会覆盖旧高分，SSO 后续转队也不会搬动历史成绩。原始记录默认受 512 MiB 字节预算保护，可用 `CHENLONG_RUN_ARCHIVE_MAX_BYTES` 在 10 GiB 上限内按正式磁盘容量设置；存满时服务返回 507 并保留既有数据，不会静默删除。交付前应按预计记录大小预留空间并验证备份。

## 8. 管理员地图发布

管理后台中的“广阳岛地图设置”默认折叠。任务1、2、3 分别提供 8、10、12 套可独立编辑的地图；管理员可以查看每支队伍在三个任务中稳定获配的地图编号，再选择任意任务和地图进行编辑。编辑器支持在底图上拖动或输入坐标，调整共 8 个点位：4 个有顺序的途径点、目标物、目标点（绿色存放点）、混淆物和障碍物。保存时以服务端校验结果为准；系统会检查点位格式、地图边界、道路可达性、与停车区的道路连通性、对象/途径点/停车起终点之间的安全间距，以及障碍物是否给车辆留下可绕行空间。未通过校验的草稿不会发布。

每一套地图都独立采用递增 `revision` 和 `baseRevision` 并发保护。若两名管理员同时编辑同一套地图，后保存的旧版本会收到冲突提示，不会静默覆盖已经发布的新版本；此时应重新加载最新地图，人工核对后再保存。发布文件由服务端原子写入对应任务和地图编号的数据目录，不得手工修改。文件缺失表示使用该地图的内置初始布局；文件存在但损坏时服务会拒绝启动，应从完整备份恢复，不要自行拼改 JSON。

服务端按不可由浏览器指定的队伍内部编号，在三个任务中分别为队伍稳定分配一套地图；同队多个账号使用相同地图，修改队伍显示名称或地图内容不会重新抽取。发布后，学员登录或重新选择任务可取得本队获配地图；仅在**新建普通单局场次**时才会把该版本冻结为实际运行和判分依据。已经创建或正在运行的场次、历史记录都继续使用各自原版本。当前学员页面不启用练习五局和筛选五局入口；仓库中为旧数据兼容保留的后端私有布局不受管理员地图发布影响。

## 9. 交付包保密

本交付包及其备份只能由组织方、管理员和授权运维人员持有，**不得发给参赛者**。参赛者只应获得比赛网站的 HTTPS 访问地址；不得向其发送源码压缩包、服务器文件或数据备份。

包内数据可能含密码哈希、队伍邀请码、官网身份映射、Python 源码、成绩和未公开地图，必须加密传输并限制解压目录权限。平台内部密钥、官网密钥、RSA 私钥、历史备份、日志和写锁不得写入普通交付包或本文档。

## 10. 离线资源与最终验收

Python 的 Pyodide、ONNX Runtime、YOLO、Three.js 等浏览器资源均随项目本地提供，参赛页面不依赖 CDN。统一平台仍包含识物工坊：其浏览器首次训练会下载约 8 MB 的 MobileNet 基础模型，完全断网赛场须提前预热每个浏览器配置文件或将模型另行本地化；官网 SSO 和成绩交换也需要官网网络。

自动测试项数量会随安全回归变化，不在本子项目说明中固定宣称最终通过数量。最终验收以实际生成的同一个交付 ZIP 在目标机运行根目录 `VERIFY-WINDOWS.cmd`、本目录 `npm test` 及赛场容量/恢复演练的完整输出为准。
