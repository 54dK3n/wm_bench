# 广阳岛 Blockly 闯关

与广阳岛 Python 项目采用同一任务、地图尺度、评分口径和自主控制能力层级的独立 Blockly 可视化编程平台。选手可以组合基础动作、导航传感、道路控制、摄像头感知、结构化数据、变量、函数、判断和循环完成三项广阳岛任务；管理员管理队伍、正式成绩和比赛地图。Blockly 与 Python 的编程表达方式不同，但都支持选手根据感知结果自行规划并执行任务。

## 当前功能

- 显式启用的独立模式支持注册与登录；用户名全局唯一，队伍名称全局唯一，同队成员使用 8 位邀请码加入。统一平台模式只接受平台签名身份。
- 参赛小组统一为小学组、初中组和高中组三组；历史 `primary_low`、`primary_high` 及两种小学年级中文名称会在启动迁移和读取时统一归入 `primary`（小学组）。
- 三项比赛任务使用同一张广阳岛底图，难度由途径点和物品数量逐步增加：
  - 任务1：4 个有序途径点，目标物、混淆物、障碍物各 1 个。
  - 任务2：6 个有序途径点，目标物、混淆物、障碍物各 2 个。
  - 任务3：8 个有序途径点，目标物、混淆物、障碍物各 3 个。
- 赛场按真实 5 米 × 3 米呈现（模拟坐标 40 × 24，1 个内部单位等于 12.5 厘米）；学生移动积木统一填写厘米。
- 工具箱包含厘米前进/后退、角度转向、抓取/松开、顺序与条件选择、重复/当/直到/计数/遍历/持续循环、基础传感、导航传感、道路控制、摄像头感知、数据与列表、等待与输出、数学逻辑、文本、变量和函数。
- 导航传感可读取任务道路锚点、任务进度、释放预判、里程计、当前道路状态和无坐标道路图。任务锚点只公开道路编号与沿路进度，不公开地图坐标；选手需要使用道路关系、传感结果和自己的算法规划路线。
- 道路控制可沿当前道路居中行驶、在节点驶入程序指定的相邻道路，并返回动作是否接受、停止原因和实际距离。它不会自动计算整条路线，也不会替选手选择出口。
- 摄像头感知可判断和列出目标物、混淆物、障碍物及存放点，读取数量、方向、距离、接近与居中状态，并进行有限步自动靠近。当前实现是广阳岛 3D 场景中的仿真感知接口，不是模型训练功能。页面也可切换到“真实小车（不计分）”：实车模式会显示仅供人工查看的摄像头实时画面，并发送前进、后退、转向、抓取、松开和停止等基础指令；画面不会提供给积木程序、保存或上传，实车也不提供定位、传感或任务状态回传，不会保存比赛记录或成绩。
- 数据与列表积木用于读取结构化传感结果、按从 1 开始的序号取列表项、统计长度及转换为文字；变量可保存中间状态，函数支持参数、返回值和包含小车动作的可复用流程。
- 除“持续巡逻”外，单个受控循环最多执行 100 次；持续巡逻一直运行到选手停止程序。每次运行最多进行 1000 次导航传感查询、1000 次摄像头查询和 300 次道路控制；函数累计最多调用 1000 次、递归最多 50 层，避免错误程序让页面失去响应。
- 100 分实时评测与 Python 赛项采用同一口径：目标物入库、混淆物完整移出道路边缘 2.5 厘米、按序通过途径点、零碰撞绕开指定障碍并返回起点共同组成任务 40 分；规则 25 分只对驶出道路和碰撞扣分；自主运行 15 分；完整完成后按时间计算效率 20 分。当前任务不设置超速、逆行、红灯或禁行区规则。
- 历史作品中的按秒移动积木仍可加载和运行，但新工具箱不再显示它，防止旧作品的“1 秒”被误当成“1 厘米”。
- 每次运行前自动恢复小车、物品和任务进度；运行只保存调试记录，学生在“我的成绩”中手动正式提交。
- 正式记录保存生成代码、Blockly 积木结构、目标完成证据、评分明细和地图修订号；后台按同一共享评分模块重新计算，不直接接受页面声称的任务分。
- 管理后台采用“正式成绩 / 用户管理 / 地图设置”三个简洁页签，列表均分页。
- 正式成绩支持用户名/队伍搜索、任务筛选、最新/分数排序，以及“每队每任务最高分”视图。
- “我的比赛记录”会自动取齐服务端分页，显示三个任务各自已正式提交的最高分，并按每页 20 条浏览；后台同样取齐正式记录后再筛选、排序、汇总和导出，按每页 15 队显示所在小组、三项最高分和三项总分。
- 管理员可拖动或输入坐标修改三项任务的途径点、目标物、目标点、混淆物和障碍物。
- 地图发布带修订号和校验摘要。学员每次运行前自动同步最新版；旧记录继续绑定原地图版本。
- 用户和正式成绩均可导出；成绩导出包含生成代码和积木结构。

本项目可独立运行，也可作为统一比赛平台中的 Blockly 编程环境运行。独立模式继续使用自己的账号、会话、地图和成绩数据；统一模式由平台网关注入短时签名身份和当前队伍获配的 Python 标准地图，Blockly 仍保留自己的运行记录与积木程序证据。

Three.js 暂时固定为已经完整回归的 0.160.0 全局构建。改为 ES Module 会同时改变脚本加载顺序、全局 `THREE` 接口和离线资源组织，需要重新执行完整 3D 视觉与交互验收，因此本次不做高风险迁移；本地供应文件只移除了该旧加载方式自身输出的弃用提示，渲染代码和 Three.js 版本均未改变。后续升级应把 Python 与 Blockly 两个模拟器一起迁移并重新做视觉基线测试。

## 启动

需要 Node.js 22.5 或更新版本，无第三方运行依赖；运行记录使用 Node 内置 SQLite。

统一平台通常由上级启动器注入 `PLATFORM_SSO_SECRET`。如需独立运行本地账号系统，必须显式设置管理员和本地认证开关：

    $env:BLOCKLY_ENABLE_LOCAL_AUTH = 'true'
    $env:BLOCKLY_BOOTSTRAP_ADMIN_USERNAME = '<管理员用户名>'
    $env:BLOCKLY_BOOTSTRAP_ADMIN_PASSWORD = '<至少10位的管理员密码>'
    npm start

默认地址：<http://127.0.0.1:6180/>

主要环境变量：

- HOST：监听地址，默认 127.0.0.1
- PORT：监听端口，默认 6180
- BLOCKLY_DATA_DIR：独立数据目录，默认项目内 .blockly-data
- BLOCKLY_PUBLIC_ORIGIN：使用公网反向代理时的唯一可信页面来源
- PLATFORM_SSO_SECRET：统一平台共享签名密钥，至少 32 个 UTF-8 字节；设置后只接受签名平台身份，本地 Cookie 和登录、注册、退出接口全部禁用
- BLOCKLY_ENABLE_LOCAL_AUTH：只有精确设为 `true` 且未启用平台模式时，才允许独立账号登录、注册和本地 Cookie
- BLOCKLY_BOOTSTRAP_ADMIN_USERNAME：独立模式首次创建的管理员用户名；不得与现有普通用户重名
- BLOCKLY_BOOTSTRAP_ADMIN_PASSWORD：独立模式首次创建管理员所用密码，10–128 个字符；不得写入源码或交付包
- BLOCKLY_MAX_USERS：独立模式账户容量，默认 2000，上限 10000；统一模式账户容量由统一 Python 账户服务控制
- BLOCKLY_STORE_WRITE_BATCH_MS：并发写入合并窗口，默认 20 毫秒，范围 0–250 毫秒

统一模式下，可信网关使用共享契约注入 `x-chenlong-platform-principal` 和 `x-chenlong-platform-map`。服务只接受 audience 为 `blockly`、尚未过期且签名正确的身份，并逐项核对三项任务的 Python canonical v2 地图、摘要、套号和原始修订号（基础地图允许修订号 0）。浏览器不能自行声明平台身份或地图；网关必须移除外部同名请求头后重新注入。缺少平台身份头时直接拒绝，不会回退到历史本地 Cookie。

账户、队伍、会话和地图仍保存在小型核心文件 `primary-blockly-store.json`，同一短时间窗口内的核心变更会合并原子落盘。不断增长的运行记录单独保存在 `primary-blockly-records.sqlite`，采用 WAL、事务提交以及 owner / team / task / state / submittedAt 组合索引，不再为每条记录同步重写整份 JSON。核心文件和 SQLite 元数据保存相同的随机数据库身份，正常重启保持不变；数据库被删除、换成空库或换成另一份同数量数据库时都会拒绝启动。数据目录仍使用单写进程锁，防止两个实例互相覆盖；写入失败时请求会明确失败，不会伪装成已经持久化。修改服务端代码后需要重启，更新和备份必须覆盖整个 `.blockly-data` 目录。

首次启动本版本时，v1–v7 核心文件中的旧记录会先原样复制为 `primary-blockly-store.pre-sqlite-<摘要>.json`，再在单个 SQLite 事务中导入并逐条核验，最后才把核心文件切换到 v8。中途失败不会删除旧 JSON；重复启动会按记录 ID 和内容摘要幂等续迁，遇到同 ID 不同内容时停止服务等待人工核查。

个人记录 `/api/records` 和管理员正式记录 `/api/admin/records` 支持 `page`、`pageSize` 服务端分页。显式分页的默认 `page=1`、`pageSize=250`，单页最大 1000；参数必须是范围内的正整数。完全不带分页参数的旧客户端仍可使用，但只返回最新 1000 条，并通过 `pagination.truncated` 明确提示是否截断。新版学生端和后台会逐页取齐，因此最高分、筛选、队伍汇总与导出不会因兼容上限漏掉旧记录。

## 测试

    npm test
    npm run test:browser
    npm run test:strict

- npm test：自动回归覆盖完整工具箱目录、积木定义与生成器、参数和边界、单位换算、评分、道路、运行重置、注册登录、地图版本、记录提交、后台详情、导出、500 人并发保存和提交、每页 500 条连续取齐 1500 条个人/后台记录，以及 2000 账号每账号 12 条记录（共 24,000 条）的迁移、索引和重启恢复测试。
- npm run test:browser：在隔离数据目录和真实 Chrome 中逐项创建并编译 80 个可见工具箱入口与 8 个变量/函数动态用例，实际运行 14 个分类的组合程序，并逐条核对自动保存、正式提交、后台程序详情、能力标记及地图编辑器。
- npm run test:strict：依次执行上述自动回归和真实浏览器矩阵，是交付前推荐使用的完整验收命令。

严格浏览器测试只创建 `e2e_` 前缀的临时账号和临时数据目录，完成后自动清理，不会写入正式用户、队伍和成绩。完整范围和结果见[积木严格测试报告](./积木严格测试报告-2026-08-27.md)。

对已启动环境进行带真实测试数据的验收：

    $env:BLOCKLY_ADMIN_USERNAME = '<管理员用户名>'
    $env:BLOCKLY_ADMIN_PASSWORD = '<管理员密码>'
    $env:BLOCKLY_TEST_URL = 'http://127.0.0.1:6180'
    $env:BLOCKLY_TEST_ORIGIN = '<页面实际来源>'
    npm run test:live

验收脚本会创建带 accept_ 前缀的测试账户和队伍，在三项任务各生成两次运行并提交最高分，同时修改再还原三张地图。
